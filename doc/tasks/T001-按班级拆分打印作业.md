# T001：按班级拆分打印作业

- 状态：待验收
- 来源：项目总控聊天
- 实施角色：执行聊天。
- 更新：2026-10-07

## 已确认需求

1. 取消程序自动生成的封面页。
2. 一班一个独立打印作业。20 班 × 每班 40 份，应产生 20 个班级作业，共 800 份有效内容。
3. 程序将每班的 40 份拼入一个 PDF，驱动对该班 PDF 打印 1 份；保留程序控制逐份顺序和双面的方式。
4. 取消 80 张拆组限制。单班即使超过 80 张，也保持一个作业，不拆成多个小组。
5. 间隔页由打印机自带的作业间隔功能提供，程序不生成间隔页，也不修改该设备功能配置。
6. 多台打印机预先平均分配班级；每个班级完整交给一台打印机。
7. 设备发生离线、卡纸或提交失败后，未开始班级留在原打印机，等待人工处理，不自动转给其他打印机。其他健康设备继续自己的作业。
8. 修复用户报告的“勾选多台打印机，但只有一台收到作业”问题。

## 实施采用的默认值

- 先针对正式 Windows 印务台客户端。独立 agent 是通过 python run.py agent 启动的另一种本地打印服务，本次不主动扩展其业务规则；共享模块调整需保持兼容。
- 按连续班级序号分段，例如 20 班、两台打印机：第一台 1–10，第二台 11–20。
- 不能整除时，各机分得的班级数最多相差 1；按设备名称、ID 升序确定稳定顺序，并在预览和后端使用相同顺序，将余数分给前面的设备。打印机多于班级时，部分设备分配 0 班并明确显示。
- “第 1–20 班”是本任务内的批次序号；当前上传只有班级数量，本次不引入真实班级名称录入。

## 已核实的当前实现

- 云端保存班级数、每班份数和总份数。桌面导入时传递总份数及包含班级数的元数据，本地并未按班级拆分。
- app/importer.py 按总份数和托盘上限拆小组；app/compose.py 在每组 PDF 前加入封面、封面背面空白，并把该小组的份数拼入 PDF。
- WindowsBackend.submit() 固定使用 duplexlong,monochrome,1x，一份合成 PDF 对应一次队列提交。
- Executor._assign_task() 将排队小组派给所选且当时空闲的设备。若只有一个小组，只会用一台；但 20 班 × 40 份通常会产生多个旧小组，因此这不足以解释用户反馈的全部情况。
- 界面允许选择“打印中”的设备，实际派发要求设备为 IDLE。需要结合真实设备状态、所选 ID、生成小组数和提交日志复现，不能预先断言唯一根因。
- 现有测试覆盖“不同任务分配到不同打印机”，未覆盖“同一任务的多个班级分配到多台打印机”。

## 实施方案

### 作业生成

- Windows 桌面以班级数生成恰好对应数量的作业，每班内容为原稿按每班份数重复；去掉封面及其专用背面空白。
- 双面奇数页原稿仍在每份末尾补白，避免后一份首页落在前一份背面。该补白不是间隔页。
- 班级 PDF 使用独立且可识别的文件名，避免暂停/取消时匹配到其他班级作业。
- 用纸统计只计算有效副本所需纸张及其双面补白布局，不计已取消的封面，也不估算打印机自行插入的间隔页。

### 预分配与执行

- 在实际派发前保存完整的“班级序号 → 目标打印机”分配关系，重启不重新分配。
- 每台设备只按序执行属于自己的班级，不从其他设备领取尚未开始的班级。
- 选机确认时显示各设备分到的班级区间/数量；机队页显示该设备对应的班级进度，避免把同一任务的全部班级进度当作每台设备的分配量。
- 任务暂停/取消仍作用于整项任务；单机故障不能用全任务暂停实现，否则会阻塞其他健康设备。
- 未开始班级保持原机等待。在机队页为故障设备提供“恢复本机分配”操作，校验设备已恢复可用后，仅恢复该任务在该设备上的未开始班级。
- 已提交但完成情况不明的班级需人工选择“确认本班已完成”或“整班重新打印”。重打需明确提示废弃本班已出纸张，并确认旧作业已停止；只处理精确匹配的本程序作业，无法确认时保持阻塞并提示在 Windows 队列处理。不得自动重打，不得再次打印已确认完成的班级；所有人工选择记录事件。
- 全部班级完成后才进入待收纸，确认取件后完成整项任务。

### 数据与兼容

- 明确传递并校验班级数、每班份数和总份数；不能通过向下取整悄悄丢失份数。旧任务元数据不完整时应明确提示，不能猜测班级拆法。
- 给班级作业及预分配数据持久化必要标识，区分新旧作业模型，保持旧任务记录可读。
- 已开始的旧任务保持原模型直至结束，不能自动重新拆分。未申请打印且未派发的旧本地任务，在首次打印前按完整云端元数据重新生成班级作业；缺失或不一致时拒绝启用打印并提示重新提交。已申请但未结束的旧任务不自动转换，需先结束或由用户取消后重新提交。

## 验收场景

- 20 班 × 40 份得到 20 个独立作业，每班完整 40 份，总有效份数 800，无程序封面或间隔页。
- 双面奇数页文件逐份顺序正确；单班超过 80 张仍只有一个作业。
- 两台打印机平均得到 10 班；三台得到 7/7/6 班，作业归属在重启后保持。
- 同一任务在两台健康设备上确实分别提交独立作业；记录所选设备、预分配、实际提交和失败原因，复现并解释原“仅一台收到”问题。
- 一台故障时，其未开始班级留在原机，另一台继续自己的班级；人工处理后不重复打印已完成班级。
- 暂停、继续、取消、完成和取件状态与班级作业一致。
- 自动化测试覆盖以上逻辑；真实佳能设备验证两台队列作业、份数、出纸顺序与设备间隔页。模拟测试通过不能替代真机验收。

## 当前结果

实现范围为正式 Windows 桌面客户端；独立 agent 保持旧任务模型。

### 实际修改

- `app/importer.py` 为桌面任务按班级生成一个合成 PDF；持久化 `job_model` 区分旧组和班级作业。旧本地任务仅在尚未申请打印、云端班级数/份数一致且原稿缓存存在时转换；已申请或信息不完整的任务拒绝转换。
- `app/compose.py` 为桌面班级作业关闭封面和封面背面，保留双面奇数页逐份补白；班级作业纸张估算不计封面且不调用 80 张拆组逻辑。共享模块的旧默认行为保留，独立 agent 继续使用封面和旧拆组限制。
- `app/station_runtime.py` 在打印请求时按打印机名称小写排序、ID 破同序，连续分配班级并写入 `groups.printer_id`。`app/executor.py` 只派发到固定设备。提交失败、离线、卡纸或完成校验不明时，班级留在原设备并阻塞人工处理，不自动转派。
- 增加原设备恢复、人工确认本班完成、或精确匹配旧 Windows 作业并经用户确认后整班重打的接口与机队界面。界面显示选择设备的班级区间预览、本机班级进度和阻塞班级操作。
- 同步了 `prototype/dist/client` 到 `app/static/desk`。仅复制本次产物文件，没有删除静态目录原有的其他文件。

### 实际验证

- `python -m unittest discover -s tests`：45 项通过。
- `npx tsc --noEmit`（`prototype` 目录）：通过。
- `npm run build`（`prototype` 目录）：两次均完成所有编译和 2 条静态路线预渲染，随后 Node 在退出阶段触发 `uv_async` 断言并以退出码 1 结束。构建命令不能记为通过；已生成并同步产物，但需在目标 Windows 构建环境修复/确认退出断言后复验。
- 尚未运行 Windows 桌面客户端、打印测试页或真实打印机；自动化结果不代表真实设备验收通过。
- 用户报告的“勾选多台仅一台收到作业”未能用现场日志复现，缺少原设备状态、所选打印机 ID、班级作业数及 Windows 队列提交日志，不能确认历史故障的具体根因。新调度路径已由自动化测试覆盖同一任务的多机独立派发。

### 真机验收待办

1. 在正式 Windows 印务台构建并启动桌面客户端，绑定至少两台真实佳能队列；修复并确认前端构建退出码正常。
2. 用 20 班 × 每班 40 份的测试 PDF 打印：核对生成 20 个独立 Windows 作业、每个作业为 1 份合成 PDF、实际含 40 份内容、无程序封面/间隔页、奇数页双面份间补白正确。确认打印机自身作业间隔功能实际生效，且程序没有改动设备功能。
3. 核对两台设备分配 10/10、三台设备 7/7/6、班级连续编号范围与设备稳定对应；重启客户端后确认分配不变，并检查各队列确实分别收到作业。
4. 逐一模拟/验证离线、卡纸和提交失败：故障设备未开始班级必须留在原设备，健康设备继续执行自己的班级；原设备恢复操作只恢复本机未开始班级。
5. 对已提交但完成状态不明的班级，验证“确认本班完成”不重打；验证整班重打前要求 Windows 旧作业停止并确认废弃旧纸，只取消精确匹配的本程序作业，不重复打印已确认完成的班级。
6. 验证整项暂停、继续、取消、全部班级完成后的待取件/确认收纸状态；采集 Windows 队列和程序事件日志，补充解释原“仅一台收到作业”问题。

仍缺少真实佳能设备、目标客户端运行结果及现场队列日志，状态保持“待验收”。不得把当前自动化测试写成真机通过。
