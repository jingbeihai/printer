## 客户端更新实施方案

编制日期：2026-10-15。状态：开发中；方案已确认并开始实施，当前成果与验收差距见本节末尾。

### 目标与首期范围

Windows 客户端支持启动后自动检查新版、手动检查、用户确认后下载安装，以及导入离线升级包。使用同一更新程序处理在线和离线升级。首期采用完整包，保留上一版与升级前数据备份；暂不做静默强制升级、增量包或云端服务自动部署。开发入口 `python run.py desktop` 可显示版本信息，但禁用安装更新，避免替换源码目录。

默认行为：启动后异步检查一次，每 24 小时最多自动检查一次；手动检查不受此限制。自动检查失败不阻塞登录与打印，手动检查显示原因。发现新版显示版本、更新说明、大小以及“下载更新”“稍后”；下载完成后由用户点击“更新并重启”。打印期间允许下载，禁止切换版本，不自动在下一次空闲时重启。

### 当前实现与约束

- `build_exe.ps1` 生成 PyInstaller 目录包，必须更新完整目录及其静态资源，不能仅替换 EXE。
- `app/desktop.py` 将配置与浏览器数据保存在 `%APPDATA%/CanonPrintDesk`；`app/station_runtime.py` 将本地数据库和打印文件放在其 `station` 子目录。更新保持这些路径和 `client_id`，不覆盖用户配置。
- `StationRuntime.stop()` 当前调用执行器停止；`Executor.stop()` 设置停止事件。尚未形成供升级使用的完整停机、等待线程与数据库关闭协议，需要补齐。
- 当前旧数据库不匹配时拒绝启动。更新不能依靠自动猜测补列，必须对支持的数据库版本提供明确迁移路径。
- 当前工作区另有打印控制、调度、前端及构建产物改动。实施时重新检查差异，协调这些文件的接口，不能覆盖或将其视为本方案已完成内容。

### 程序布局与首次接入

建议按当前 Windows 用户安装到 `%LOCALAPPDATA%/CanonPrintDesk`，减少管理员权限需求。目录包含固定启动器、独立更新程序、`versions/<版本号>`、下载暂存区和更新事务记录；业务数据仍留在原 APPDATA 目录。

启动器读取当前版本指针，更新程序将完整新包解压到新的版本目录，通过原子替换指针切换版本。旧程序不被原地覆盖，快捷方式始终指向启动器。启动器和更新程序使用独立版本号，首期仅通过手动安装包升级自身；若新应用要求更高更新器版本，提示下载新版安装包。

现有客户端没有检查更新能力，首次必须由用户关闭旧客户端后运行一次安装包，安装带启动器和更新器的新版本。安装过程复用原数据，检测旧进程占用并阻止并行运行，不自动清理旧便携目录。以后在线升级和离线导入均进入统一流程。直接运行版本目录中的 EXE 也必须遵守同一实例锁与更新锁。

### 发布信息与包校验

拟使用现有 HTTPS 域名提供稳定版版本清单，升级包放在对象存储或静态下载目录。最终域名、存储位置及发布账号在正式发布前确定，代码不硬编码尚未确认的地址。

清单至少包含：清单格式版本、应用版本、单调递增发布序号、Windows 架构、发布时间、到期时间、更新说明、包地址、压缩和解压大小、SHA-256、最低更新器版本、服务端协议兼容范围、本地数据库来源与目标版本、签名密钥编号。

采用 HTTPS 下载、签名清单和 SHA-256 联合校验：客户端内置可信公钥，发布私钥留在发布环境，不进入仓库或客户端。实施选型采用成熟签名库，签名覆盖确定字节格式的全部清单字段，校验后才使用包地址。拒绝签名无效、过期、架构不符和低于已接受发布序号的清单；恢复上一版仅由本地恢复流程授权，不当作常规远端降级。Windows 安装包签名证书单独准备，不与清单签名混用。

下载设超时、大小上限和磁盘空间预检，失败保留旧版；首期失败可重新下载。解压拒绝绝对路径、目录穿越、链接及超出允许体积的内容。更新器只接受安装目录内已验证的暂存包，并再次校验签名与哈希。离线包携带同一签名清单，遵守同样规则。

### 更新流程与打印保护

1. 检查版本并显示说明；用户选择下载，完成签名、大小、哈希和兼容性校验。
2. 用户点击更新后取得更新锁，阻止新的打印、重打、任务分配及其他本地写操作。该状态须覆盖桌面接口和后台调度，不能只禁用界面按钮。
3. 首期保守条件：本地已请求打印的任务全部结束、无在途下载或提交、无未确认故障/待收纸状态，受管理 Windows 打印队列为空且设备无活动作业。云端尚未领取的任务不阻止升级。无法确定设备/队列状态时停止本次安装并说明原因，不取消任何 Windows 作业。
4. 在调度锁保护下重新核对条件，暂停同步，等待执行器、同步、下载与打印提交线程退出，确认数据落盘并关闭连接。等待超时则取消更新、恢复运行，禁止强杀打印相关进程。
5. 更新器等待主进程退出，核对单实例锁，备份数据，将新版本放入独立目录并记录事务阶段，然后切换版本指针。
6. 新版本以升级验证模式启动：先核验/迁移数据库、加载配置并启动本地页面，暂不启用打印调度、云端写入和用户业务写入。向更新器返回带事务标识的就绪确认。
7. 更新器确认版本与事务匹配后提交更新记录，解除业务阻断并恢复正常运行。云端短时不可达不单独判定安装失败；已知协议不兼容时禁止安装。

更新事务状态持久化为“准备、已备份、已切换、待确认、已提交、恢复中”，每一步可重复执行。进程崩溃或断电后由启动器读取事务恢复，不能仅凭进程存在就判断升级成功。

### 数据迁移与恢复

- 首期更新机制本身不修改业务表。建立显式 schema 版本记录；未版本化的已知结构先只读识别，未知或缺字段旧库给出人工迁移指引，不默认为当前结构。
- 每条迁移声明来源版本、目标版本和兼容范围，事务执行且可安全重试。备份在业务写入全部停止后用 SQLite 备份接口生成，并验证备份可读；同时保存配置和版本记录，保持浏览器数据路径及打印文件不变。
- 新版验证阶段失败且尚未开放业务时，可恢复备份数据库、配置与上一版指针，再启动旧版；恢复前确认新版进程和数据库句柄已释放。恢复失败保留现场，显示备份路径与人工处理方式，不循环尝试启动。
- 新版开始正常业务后，不自动用旧备份覆盖数据库，以免丢失新任务。此时需兼容旧版的数据库或专门恢复方案；恢复到旧程序不等于恢复了外部打印和云端状态。
- 至少保留上一版和对应升级前备份。首期提供明确的人工清理入口，不在更新失败时清理证据或自动删除业务数据。
